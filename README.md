# CRM Vova

CRM со встроенным движком бизнес-процессов на .NET 10 и React. Этап 0: ядро продаж и работающий исполнитель процессов.

[![CI](https://github.com/Vadimyass/CRM-Vova/actions/workflows/ci.yml/badge.svg)](https://github.com/Vadimyass/CRM-Vova/actions/workflows/ci.yml)

## Что уже работает

- **Домен продаж**: лиды, контрагенты, контакты, сделки со стадиями и историей стадий, активности, кастомные поля через `CustomData`.
- **Движок процессов** (`Crm.Bpm`): токенный исполнитель по подмножеству BPMN — старт, завершение, задача пользователю, авто-действия, эксклюзивный и параллельный шлюзы, таймер. Версионирование определений: запущенные экземпляры доигрывают на своей версии.
- **Триггеры от данных**: доменные события уходят в outbox, фоновый воркер разбирает их и стартует процессы. Процесс никогда не выполняется внутри пользовательского запроса.
- **Выражения**: собственный вычислитель на белом списке контекста (`vars`, `entity`, `now`, `userId`). Пользовательский код в рантайме не компилируется — это дыра в безопасности и утечка сборок.
- **API** (`Crm.Api`): минимальные эндпоинты для лидов, сделок, стадий, задач и мониторинга процессов.
- **Фронт** (`frontend`): лиды, канбан-воронка с drag-n-drop, инбокс задач, монитор процессов с журналом выполнения.
- **Два демо-процесса**, которые задействуют все поддерживаемые элементы: `lead-created` (авто-задача → таймер 2 мин → авто-задача) и `opportunity-stage-changed` (задача пользователю → шлюз → запись в поле).

## Чего ещё нет

Хранение в памяти вместо PostgreSQL, аутентификация, права на записи, BPMN-дизайнер, дашборды.

## Запуск в один клик

Двойной клик по **«Запуск CRM.command»** в Finder. Скрипт сам проверит .NET и Node, при первом запуске поставит зависимости фронта, соберёт бэкенд, поднимет API и фронт и откроет браузер.

- **Запуск CRM.command** — запустить всё и открыть интерфейс
- **Остановка CRM.command** — погасить, если окно терминала закрыли не по-человечески
- **Тесты движка.command** — прогнать тесты процессов
- **Проверка окружения.command** — показать, где нашлись .NET и Node, какие SDK стоят и свободны ли порты

Остановка: Ctrl+C в окне терминала или просто закрыть его.

Требования: **.NET SDK 10** (`brew install --cask dotnet-sdk`) и **Node.js 20+** (`brew install node`). Если чего-то нет, скрипт скажет об этом и подскажет команду.

Если macOS откажется открывать файл («не удалось проверить разработчика») — правый клик по нему → «Открыть» → «Открыть».

### Если brew ругается на симлинк

`Error: dotnet-sdk: It seems the symlink source '/usr/local/share/dotnet/dotnet' is not there` означает, что SDK поставился, но не туда, куда brew ожидал: x64-пакет на Apple Silicon кладёт бинарник в подпапку `x64`. Сам SDK при этом рабочий — скрипты ищут его и там тоже. Запусти «Проверка окружения.command», она покажет найденный путь.

Чтобы вернуть привычный `dotnet` в PATH:

```bash
sudo ln -sfn /usr/local/share/dotnet/x64/dotnet /usr/local/bin/dotnet
```

На Apple Silicon правильнее поставить arm64-сборку SDK — x64 работает через Rosetta и заметно медленнее собирает.

Логи запуска лежат в `logs/`: `api.log`, `web.log`, `build.log`.

### Запуск руками

```bash
dotnet run --project src/Crm.Api          # http://localhost:5080
cd frontend && npm install && npm run dev # http://localhost:5173
```

Фронт проксирует `/api` на `http://localhost:5080`, отдельная настройка CORS для dev не нужна.

## Тесты

```bash
dotnet run --project tests/Crm.Bpm.Tests
```

Десять сценариев движка: линейный процесс, ветвление, ожидание на задаче, параллельный fork/join, таймер, идемпотентность повторного возобновления, падение обработчика, версионирование, валидация схемы, вычислитель выражений.

## Репозиторий и CI

Первый пуш в пустой репозиторий на GitHub:

```bash
git remote add origin git@github.com:<логин>/<репозиторий>.git
git push -u origin main
```

`.github/workflows/ci.yml` гоняет на каждый push и pull request три вещи:

1. `dotnet build` всего решения в Release
2. тесты движка процессов
3. сквозной сценарий через живой API (`scripts/ci-smoke.sh`) — создание лида, автостарт процесса, квалификация, смена стадии, задача, согласование, завершение

Плюс две отдельные job: типы и сборка фронта, а также сборка Docker-образа с проверкой, что контейнер отдаёт и SPA, и API. Внешних NuGet-пакетов в проекте нет, поэтому restore в CI ничего не тянет и падать там нечему.

Сквозной сценарий можно гонять и локально:

```bash
dotnet build CrmVova.slnx -c Release
./scripts/ci-smoke.sh
```

## Docker

`Dockerfile` собирает один образ на всё: фронт компилируется и кладётся в `wwwroot` рядом с API, поэтому в проде нет отдельного веб-сервера и настройки CORS.

```bash
docker compose -f deploy/docker-compose.prod.yml up --build   # http://localhost:8080
```

Локально образ не собирался — в среде, где я работаю, нет docker-демона. Поведение одного контейнера (SPA на `/`, API на `/api`, честный 404) проверено на собранном `dotnet publish` с положенным рядом фронтом, а саму сборку образа проверяет CI.

В контейнере `/` отдаёт SPA, справка по API переехала на `/api`, неизвестный `/api/...` честно возвращает 404, а не страницу приложения. В dev-режиме `wwwroot` нет, статика не подключается и всё работает через Vite как раньше.

Данные пока в памяти: перезапуск контейнера обнуляет CRM. Postgres появится здесь на этапе 1.

## Структура

```
src/Crm.Domain          сущности, доменные события, инварианты
src/Crm.Contracts       DTO для API
src/Crm.Bpm             модель процессов, исполнитель, выражения, in-memory хранилища
src/Crm.Application     сценарии использования, порты репозиториев, диспетчер триггеров
src/Crm.Infrastructure  реализации портов, обработчики авто-действий, фоновые воркеры
src/Crm.Api             хост, эндпоинты, сидинг демо-данных
tests/Crm.Bpm.Tests     тесты движка без внешнего фреймворка
frontend                Vite + React + TypeScript
deploy                  docker-compose с PostgreSQL для следующего этапа
scripts                 запуск, остановка, диагностика, сквозной сценарий
.github/workflows       CI
```

## Секреты

В репозитории их нет и не будет. Локально — `.env` (см. `.env.example`) или `dotnet user-secrets`, в CI и проде — Secrets репозитория и переменные окружения. В `appsettings.json` попадают только безопасные значения по умолчанию.

Отдельная job в CI гоняет `./scripts/check-secrets.sh` на каждый push: скрипт проверяет и запрещённые файлы в индексе, и характерные шаблоны в содержимом. Подробности и порядок действий при утечке — в [SECURITY.md](SECURITY.md).

Демо-данные в `DemoDataSeeder` и оба демо-процесса вымышленные. Реальные данные CRM, регламенты и внутренние документы по проекту в репозиторий не попадают.

# Безопасность

## Где живут секреты

В репозитории секретов нет и не должно появиться. Маршруты для них:

| Где | Для чего |
|---|---|
| `.env` рядом с проектом | локальная разработка, файл в `.gitignore` |
| `dotnet user-secrets` | локальные секреты бэкенда вне рабочей папки, в профиле пользователя |
| Secrets репозитория на GitHub | CI и деплой |
| Переменные окружения контейнера | прод |

В `appsettings.json` попадают только безопасные значения по умолчанию: порты, уровни логирования, разрешённые origin. Всё, что нельзя показать, приходит из окружения.

Проверка: `./scripts/check-secrets.sh` — гоняется в CI на каждый push и ловит как запрещённые файлы в индексе, так и характерные шаблоны в содержимом.

## Что не попадает в репозиторий

- Реальные данные CRM: выгрузки, дампы, письма, имена клиентов. Демо-данные в `DemoDataSeeder` вымышленные.
- Процессы, описывающие реальные внутренние регламенты компании. В репозитории лежат только демонстрационные.
- Внутренние документы по проекту — план, оценки, статусы. Они живут отдельно.

## Если секрет всё-таки попал в коммит

Смена значения важнее вычистки истории. Порядок: отозвать и перевыпустить секрет, потом удалить из истории (`git filter-repo`) и сделать force-push. Пока изменения не запушены, достаточно `git commit --amend` или интерактивного rebase.

## Сообщить об уязвимости

Через приватный security advisory в разделе Security репозитория. Публичные issue для этого не подходят.
